# ツールのバージョン更新とリリース

このリポジトリ専用の手順。[AGENTS.md](../../../AGENTS.md)のブランチ・本人名義・データ保全・レビューの規則を基準にする。バージョン番号・テスト件数・DB構造をこのSkillへ固定しない。

## 依頼と作業場所を確認する

「開発ブランチの準備」「表示バージョンの更新」「公開」「中断した公開の再開」を区別する。対象バージョンはユーザーの指示から決め、未指定なら既存資料と公開状態を調べてから必要な点を質問する。次のバージョンやMVPの範囲を独断で決めない。

バージョン更新だけではmain更新・タグ作成・公開を行わない。明示的なリリース依頼はその公開の承認として扱い、同じ承認を再度求めない。ユーザーレビューの完了状態は個別の根拠に基づく。公開の承認だけで全機能をレビュー済みにしない。

プロジェクトルートと上位の指示、Claude向けの指示を確認し、次を調べる。

```sh
pwd
git status --short --branch
git diff --stat
git worktree list
git remote -v
git log -5 --oneline
```

既存の未コミット変更を保ち、対象の`codex/release/<バージョン>`で作業する。新規ブランチは直前の公開タグから作る。公開タグ・main・既存のリリースブランチが一致しない場合は履歴と理由を確認し、未確認の差分を混ぜない。必要なら専用worktreeを使う。稼働中の別worktreeを切り替えない。

リモートとGitHubの実際の状態も確認する。現在利用できるGitHub連携で機能が足りない場合は、認証済み`gh`・Gitを使う。認証情報そのものは出力しない。APIの権限不足を理由に、機能する既存認証の権限を不用意に広げない。

公開後に依頼されたSkill・開発手順だけの変更は、公開タグから別の`codex/<作業名>`ブランチで扱う。公開済みタグやコミットを変更せず、そのためだけに次のアプリバージョンを作らない。

## バージョンと関連資料を揃える

正本は`package.json`の`version`。`package-lock.json`のトップレベルと`packages[""].version`も同じ値にする。番号の更新にGitタグや依存パッケージの更新を混ぜない。

画面下部は`src/AppFooter.tsx`がpackage.jsonを参照する。月次・年間・バックアップの3画面で表示を確認する。ブラウザテストのバージョン期待値も確認する。

`rg`で旧番号と対象番号を探し、README・手動／Agent向け初期セットアップ資料の配布タグ、clone・更新コマンド、画面と保存の説明を現行へ揃える。移行・復元に必要な過去の番号や判断記録は一括置換しない。

挙動やデータ構造に変更がある場合は、[sync-spec-db](../sync-spec-db/SKILL.md)を使って要求仕様書・仕様管理・DB資料・関連図を照合する。コード反映済みと検証・ユーザーレビュー完了を区別し、未確認事項は残す。手順・Skillだけの変更でアプリ仕様やDB資料を書き換えない。

## 公開候補を検証する

`package.json`のNode.js要件と現在の検証コマンドを読み、アプリのリリースでは次を実行する。失敗・未実施を成功に含めない。

```sh
npm test
npm run test:mock
npm run build
npm run format:check
git diff --check
```

画面の変更はREADMEに従い、ビルド後に`node --test tests/browser/monthly-entry.mjs`も実行する。Playwrightが環境に備わる場合は`PLAYWRIGHT_MODULE`へ実在するモジュールパスを指定する。通常起動のためにPlaywrightを追加しない。テストは専用ポート・架空データ・メモリDBを使う。対象操作と3画面のバージョンを確認し、タッチイベントの検証と実機タッチのレビューを区別する。

文書・Skillだけの変更はリンク・内容・Skillの検証など、その変更に合う確認を行う。アプリのテストを形だけ追加しない。

## 本人名義で候補をコミットする

リポジトリローカルの`user.name`・`user.email`・`user.useConfigOnly`と、作者・コミッターへの環境変数等の上書きを確認する。グローバル設定を変えない。

```sh
git config --local --get-regexp '^user\.'
git var GIT_AUTHOR_IDENT
git var GIT_COMMITTER_IDENT
```

実メールのGitHubへの紐付けは、認証ユーザーと検証済みのコミット情報等で確認する。メール一覧APIが利用できなければ、既存コミットの作者・コミッターのemailとGitHubアカウントの対応でも確認できる。本人情報が未確認・不一致・noreplyなら新規コミットを作らない。

今回の対象ファイルを列挙してステージし、`git diff --cached --name-status`と本文を確認する。DB・バックアップ・認証情報・実データ・利用者の個人名・環境固有の絶対パス・無関係な既存変更を含めない。Conventional Commitsでコミットしたら`git show -s --format=fuller HEAD`を確認し、push前にも前回公開以降に作成した全コミットの名義を照合する。公開済みの古い名義をこの作業で修正しない。

公開候補のコミットだけを別フォルダへcloneし、clone先のHEADが確定したSHAと一致することを確認する。clone先を実際の作業ディレクトリにして`npm ci`と`npm run build`を実行する。`npm --prefix`で元ディレクトリから代用しない。空DBで起動し、3画面・静的ファイルの配信、架空データの保存と再起動後の保持を確認する。通常DB・認証情報・既存バックアップをコピーしない。スキーマ変更があれば、架空DBでの移行・復元も確認する。

候補に修正を加えたら、影響する検証とclone確認をやり直し、公開するSHAを確定する。

## 公開し、結果を確認する

公開依頼があるときは[公開・中断再開の手順](references/publish.md)を読む。実施済みの範囲を確認してから進める。

完了報告には公開URL・バージョン、検証結果、残る未確認事項を示す。main・タグ・Releaseが同じ検証済みコミットを指すことを確認してから公開完了とする。コードの公開と利用者PCへの更新は区別し、PCの更新を依頼されていなければ稼働中データを切り替えない。
